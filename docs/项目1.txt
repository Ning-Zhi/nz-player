# 一、两个方案的对比分析

先说结论：**两个方案的定位判断完全一致（无人值守播放器而非电视大全），核心思路高度重合，但各自的优势分布在不同层面**——方案A（我此前给的）强在**工程落地细节**，方案B强在**体系化表达**。

## 1.1 共识部分（说明是方案核心，直接保留）

| 共识点 | 说明 |
|---|---|
| 定位 | 无人值守、单频道锁定、故障自愈，做减法而非加法 |
| 播放器 | ExoPlayer首选，ijkplayer备选 |
| 重连 | 指数退避 + 30秒周期封顶，永不放弃 |
| 保活 | 前台服务 + 崩溃自启 + 开机自启 |
| UI | 极简、状态透明、自动隐藏 |
| 实施 | 分四阶段，先跑通再加固 |

## 1.2 差异对比与整合裁决

| 维度 | 方案A | 方案B | 裁决 |
|---|---|---|---|
| 架构表达 | 模块拼图 | 四层分层架构 | **取B的分层框架**，更清晰规范 |
| 卡死检测 | 播放器帧回调（15秒无新帧） | 截屏像素比对（10秒） | **融合**：帧回调为主（零开销、播放器hang住时“无回调”本身就是信号），截屏比对做可配置兜底 |
| 重连分级 | stop→prepare→play 一级 | 软重连（保留Surface）/硬重连（重建）两级 | **取B**，软硬分级可减少黑屏闪烁，更精细 |
| 网络探测 | ping网关+公网DNS+HTTP HEAD三重验证 | ping网关/DNS | **取A**，单ping存在“假联网”，三重验证更严谨 |
| 频道列表 | 有列表 + 频道锁定开关 | 完全不提供列表 | **取A**。你说“只能固定台”是指断网时不许自动跳台，但你播的是多个地方频道，日常仍需手动切台，“列表+锁定开关”才贴合真实使用 |
| 双内核 | ExoPlayer+ijk，且**每个频道记住内核偏好** | 三选一，未提偏好记忆 | **取A**，电视大全类源格式杂，不同台适配不同内核是实战必需 |
| 长稳运维 | 每日定时自愈重启、内存水位监控、日志轮转 | 无 | **取A**，这是7×24场景独有且必需的，B缺失 |
| 配置管理 | 本地配置文件 | 本地配置 + **局域网HTTP远程改配置** | **取B并扩展**，远程管理能大幅减少你跑现场的次数 |
| 异常场景清单 | 无系统化清单 | 有覆盖清单 | **取B并扩展**为验收标准 |
| 双进程守护 | 未提 | 提及 | **降级为可选增强项**。电视盒子魔改ROM多（不少还是Android 4.4/低版本），双进程互拉在部分ROM上无效甚至触发更激进查杀；前台服务+崩溃自启已覆盖主场景 |
| 部署建议 | 网线直连、屏幕永不休眠、72小时压测 | 电池白名单引导 | **合并**，系统层设置是“卡掉软件”的常见元凶 |

## 1.3 方案B需要修正的两点

1. **“不提供频道列表UI”过于绝对**——与你的实际使用（多个地方台）冲突，误操作问题用“锁定开关+设置二次确认”解决即可。
2. **双进程守护在盒子环境不可靠**——不能作为主依赖，否则会给人“已保活”的错觉。

## 1 项目概述

### 1.1 项目背景

现有使用场景：电视盒子7×24小时不间断播放地方电视频道，频道源主要来自网络上“电视大全”类应用收集的直播地址，操作方式为鼠标。

当前使用的通用直播App存在三大问题，导致需要人工频繁干预：

1. 网卡或设备卡顿时，软件被杀掉或崩溃，需人工重新打开；
2. 断网后App自动跳播放源或跳台，无法固定在指定频道；
3. 画面卡死后需手动点击一下才恢复。

### 1.2 项目目标

开发一款**无人值守直播播放器**：锁定指定频道，遇到断网、卡死、崩溃等一切异常时自动恢复，恢复后**必须回到原频道原源**，将人工干预次数降到趋近于零。

### 1.3 与通用直播App的本质区别

| 维度 | 通用直播App | 本项目 |
|---|---|---|
| 设计目标 | 人主动观看，交互丰富 | 无人值守，自愈优先 |
| 异常处理 | 播不了就换源换台 | 认准一个台，死磕到底 |
| 功能策略 | 功能越多越好 | 功能砍到最少，越简单越稳定 |

### 1.4 名词定义

- **源（URL）**：一个频道的直播流地址，格式通常为 HLS(m3u8)、HTTP-TS、RTMP 等；
- **频道**：一个电视台，可对应主源+备用源；
- **软重连**：重置播放器但不重建渲染Surface，画面闪断短；
- **硬重连**：完全释放并重建播放器实例，恢复能力最强但会黑屏一下；
- **看门狗**：独立于播放逻辑、持续监测播放健康状态并触发恢复的机制。

## 2 需求分析

### 2.1 现状问题根因分析

| # | 现象 | 根因 | 对策方向 |
|---|---|---|---|
| 1 | 网卡/设备卡时软件被卡掉 | 系统内存吃紧杀后台；播放器内存泄漏；解码崩溃；部分ROM锁屏/休眠时断WiFi | 前台服务保活 + 崩溃自启 + 内存监控 + 定时自愈重启 + 系统设置引导 |
| 2 | 断网后跳源跳台 | 通用App内置“播不了就换”的容错逻辑 | 彻底禁用一切自动换源/换台逻辑，频道锁定 |
| 3 | 画面卡死，点击一下才动 | 直播流丢包后播放器状态机卡在缓冲/解码等待态，无自动重置 | 看门狗监测画面停滞，自动执行重置 |

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-01 | 固定频道播放：启动后自动恢复上次频道，播放中任何异常恢复后回到**同一频道同一源** | P0 |
| FR-02 | 自动重连：断流后按指数退避重试，稳定在30秒周期，网络恢复后立即触发重连 | P0 |
| FR-03 | 卡死自愈：画面停滞超阈值后自动重置播放，无需人工点击 | P0 |
| FR-04 | 崩溃恢复：App崩溃后数秒内自动重启并恢复频道；盒子重启后开机自启 | P0 |
| FR-05 | 频道管理：支持m3u导入与手动添加，提供频道列表供**手动**切换，配频道锁定开关防误操作 | P1 |
| FR-06 | 配置管理：本地配置文件（U盘可改）+ 局域网Web远程修改 | P1 |
| FR-07 | 状态可视化：屏幕角落常驻状态指示（正常/重连中/等待网络），可查看运行时长、当日断线次数 | P1 |

### 2.3 非功能性需求

- **稳定性**：连续运行72小时无人工干预（验收指标）；
- **资源**：常驻内存目标 ≤ 150MB（视盒子配置），低端盒子可裁剪；
- **操作**：同时支持鼠标与遥控器（方向键+OK键）；
- **兼容性**：适配盒子实际Android版本（见3.3选型决策表）；
- **可维护性**：所有异常事件留痕可查，支持远程诊断。

## 3 总体设计

### 3.1 设计原则

1. **单频道锁定**——一切自动切换逻辑物理上不存在；
2. **自愈优先**——任何异常不需要人工；
3. **软恢复优于硬恢复**——先试代价小的手段，减少画面闪断；
4. **少即是多**——功能极简，降低出错面；
5. **状态透明**——异常可见但不打断。

### 3.2 系统架构

```
┌───────────────────────────────────────────────┐
│  UI层：全屏播放画面 / 状态浮层 / 频道列表 / 设置面板  │
├───────────────────────────────────────────────┤
│  播放控制层：                                     │
│   播放内核管理(ExoPlayer主/ijk备/每频道内核偏好)      │
│   缓冲策略管理 / Surface生命周期管理                 │
├───────────────────────────────────────────────┤
│  容错引擎层（核心）：                               │
│   三层故障检测(网络层/传输层/渲染层)                  │
│   自愈状态机(软重连→硬重连→休眠等待)                 │
│   重连调度器(指数退避+30s周期+恢复即连)              │
├───────────────────────────────────────────────┤
│  保活与运维层：                                    │
│   前台服务 / 崩溃捕获自启 / 开机自启 / WakeLock+WifiLock │

├───────────────────────────────────────────────┤

└───────────────────────────────────────────────┘
```

### 3.3 技术选型

**系统版本适配决策表**（关键前提：先确认盒子Android版本）：

| 盒子系统 | 播放内核方案 | 说明 |
|---|---|---|
| Android 5.0 (API 21)+ | ExoPlayer/Media3（首选）+ ijkplayer备选 | Media3 要求 API 21+ |
| Android 4.4 (API 19) | 老版 ExoPlayer 2.x 或 ijkplayer 为主 | 大量老盒子为4.4/1G内存，Media3不兼容 |

其他选型：

| 组件 | 选型 | 说明 |
|---|---|---|
| 主播放内核 | ExoPlayer (Media3) | 官方维护，HLS支持好，状态回调完善，便于实现重连逻辑 |
| 备用内核 | ijkplayer | 基于FFmpeg，对HTTP-TS/RTMP等杂源兼容性好 |
| 每频道内核偏好 | 频道配置中可指定 `player: exo / ijk` | 某台用Exo反复解码错误时单独指定，其余不受影响 |

| 远程配置 | App内嵌轻量HTTP服务（如NanoHTTPD） | 局域网浏览器直接改配置 |

## 4 详细设计

### 4.1 播放内核管理模块

- 双内核并存，默认ExoPlayer；
- 每频道可配置并**记忆**内核偏好，解码连续失败时提示（或自动）切换该频道的内核，不影响其他频道；
- 解码异常时的处理链：解码错误 → 记录 → 软重连 → 仍解码错误 → 该频道切换内核硬重连；
- 直播缓冲策略：针对弱网配置较大的播放缓冲（如 `DEFAULT_MIN_BUFFER_MS` 提升至15~30秒），用少量延迟换取抗抖动能力——无人值守场景延迟不敏感，稳定优先。

### 4.2 频道锁定模块

- 配置中固化「当前频道ID + 当前源URL」，启动即恢复；
- **重连时只做一件事：重新load同一个URL**，不遍历源列表、不切台，跳台逻辑在代码层面不存在；
- 备用源策略（默认关闭，可开启）：开启后仅允许在**同一频道**的主源/备源间切换，且必须满足「连续失败 ≥ 阈值（默认10次或5分钟）」才切换一次，切换后锁定新源继续重连；
- 频道锁定开关：开启后，鼠标点击画面/频道列表操作均被忽略（防误触），解锁需在设置面板二次确认；
- 支持m3u/m3u8播放列表导入 + 单条URL手动添加。

### 4.3 三层故障检测体系

| 层级 | 检测对象 | 检测方式 | 触发条件（默认值，可配置） |
|---|---|---|---|
| **网络层** | 设备联网状态 | 系统NetworkCallback监听 + 主动探测：ping网关 + ping公网DNS(114.114.114.114) + HTTP HEAD三重验证 | 探测失败判定断网 |
| **传输层** | 直播流数据 | 播放器BUFFERING状态持续时长、下行码率 | 持续BUFFERING ≥ 10秒且无进展 |
| **渲染层** | 画面是否真在动 | **主**：ExoPlayer帧渲染回调，监控“距上次新帧的时长”（播放器线程hang住时恰好收不到回调，定时器超时即判卡死）；**兜底（可配置）**：低频截屏比对像素哈希 | 连续 ≥ 15秒无新帧/画面无变化 |

说明：帧回调方案零额外开销且自洽；截屏比对作为兜底开关，默认关闭（低端盒子截屏有开销），仅在帧回调异常排查困难时启用。

### 4.4 自愈状态机与重连调度（核心）

```
                 [检测到异常]
                      │
                      ▼
              缓冲等待期(5秒) ──[自行恢复]──► 正常播放
                      │[未恢复]
                      ▼
        ┌──────────────────────────┐
        │ 软重连 (最多3次)           │  重置播放器prepare
        │ stop→prepare→play         │  保留Surface，闪断最短
        └──────────────────────────┘
                      │[3次失败]
                      ▼
        ┌──────────────────────────┐
        │ 硬重连 (最多3次)           │  完全释放重建播放器
        │ 释放内核→重建→重新load      │  恢复能力最强
        └──────────────────────────┘
                      │[仍失败]
                      ▼
        ┌──────────────────────────┐
        │ 休眠等待模式               │  屏幕提示"信号中断"
        │ 30秒周期探测网络+重试       │  显示倒计时+重试次数
        └──────────────────────────┘
                      │[网络恢复探测成功]
                      ▼
              立即重连(不等满30秒) ──► 正常播放
```

**重连节奏（指数退避 + 30秒封顶）：**

| 第N次失败 | 距上次重试间隔 |
|---|---|
| 1 | 立即 |
| 2 | 5秒 |
| 3 | 15秒 |
| ≥4 | 固定30秒，无限循环，永不放弃 |

**两项关键优化：**
- 网络探测成功（网关通+公网通+HTTP HEAD通）时**立即触发重连**，不必等满30秒——快速捕捉短暂掉线后的恢复窗口；
- 休眠等待期间屏幕显示“网络已断开，正在等待恢复…”而非黑屏，路过一眼即可分辨是网的问题还是盒子的问题。

**断网期间的探测频率**：每30秒一轮三重探测，避免高频重试空耗CPU和电量。

### 4.5 进程保活与崩溃恢复

| 机制 | 实现 | 备注 |
|---|---|---|
| 前台服务 | Foreground Service + 常驻通知 | 主保活手段，提高进程优先级 |
| 崩溃自启 | 全局UncaughtExceptionHandler：写日志 → AlarmManager延时3秒 → 自动重启App → 直接恢复崩溃前频道 | 同时捕获ANR |
| 开机自启 | 监听BOOT_COMPLETED，启动后恢复频道 | 盒子断电重启后免人工 |
| 唤醒锁 | WakeLock(SCREEN_BRIGHT_KEEP) + WifiLock | 防止WiFi休眠断流（老盒子常见坑） |
| 系统白名单 | 引导设置：电池优化忽略、自启动允许 | 首次启动向导中带截图指引 |
| 双进程守护 | 守护进程监控主进程心跳并拉起 | **可选增强项**：魔改ROM上效果不一，不作主依赖 |

### 4.6 长稳运行维护（7×24专项）

1. **每日定时自愈重启**：默认凌晨4:00，App自我重启一次，清掉内存碎片与累积泄漏，播放中断几秒换全天稳定；
2. **内存水位监控**：超阈值（如250MB）先软重启播放器，连续超阈值则重启App，均自动恢复频道；
3. **日志轮转**：本地记录每次断线/卡死/崩溃/重启的时间、错误类型、恢复耗时、当时频道；只保留最近7天，循环覆盖；
4. **运行统计**：本次连续运行时长、今日断线次数、今日卡死次数、当前重试计数，状态浮层中可查看——出问题先看统计即可判断是网络、源还是盒子。

### 4.7 配置管理模块

配置文件路径：`/sdcard/守播/config.json`（U盘直接替换即生效，改完自动热加载）。

远程配置：App内嵌HTTP服务（如NanoHTTPD），局域网内电脑/手机浏览器访问 `http://盒子IP:8080` 即可查看状态、修改配置、切换频道、手动触发重启——**减少跑到现场的操作次数**。

| 设置 | 状态栏入口（二次确认） | 菜单键（二次确认） | 修改地址、重连参数、锁定开关 |
| 立即重试 | 点击浮层按钮 | OK键 | 异常等待时跳过倒计时 |

设计要点：按钮做大（适合鼠标点）；5秒无操作隐藏一切UI，防误触且画面干净；频道锁定开启时，误点画面无任何副作用。

## 6 部署方案

### 6.1 盒子系统设置（首次部署必做）

1. 显示设置：**屏幕永不休眠**（休眠断WiFi是“软件卡掉”的常见元凶）；
2. 电源：性能模式/充电时常亮；
3. 应用管理：本App允许自启动、忽略电池优化（如有该项）；
4. 开发者选项：如有限制后台进程的设置，保持默认不动。

### 6.2 网络环境建议（按优先级）

1. **强烈建议网线直连**——无线网卡24小时场景的抖动是当前一半问题的来源，有线一劳永逸；
2. 若必须无线：盒子置于路由器信号良好位置，路由器为本设备做DHCP静态绑定；
3. 网络出口保留备用链路（如4G路由备份，可选）。

### 6.3 播放源建议

- 逐个测试地方台源，把**最稳定的URL固化进配置**，不依赖在线更新（电视大全类源多为盗链，随时失效）；
- 每个频道配置主源+备源；
- 条件允许时优先使用运营商IPTV专网源或有授权转发源，稳定性高一个数量级，且规避版权风险。

## 8 测试计划

1. **模块测试**：状态机各转换路径、配置热加载、内核切换；
2. **故障注入**：路由器定时断网/限速、iptables丢包、篡改源URL返回403/404、模拟源推流中断——逐条过第5章验收清单；
3. **弱网模拟**：限速至500kbps、丢包率5%/10%/20%下的缓冲与恢复表现；
4. **长稳测试**：真机连续72小时，采集内存曲线、断线次数、恢复耗时；
5. **兼容性**：以你实际的盒子型号为准（见附录C待确认项），至少覆盖该型号 + 一台备用型号。

## 9 风险分析与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 源本身不稳定（最大风险） | 高 | 软件只能保证“不停重连”，源三天两头挂则无解；先摸清源质量，优先固化稳定源/备源 |
| 盒子ROM魔改导致保活失效 | 中 | 上线前在真机72小时压测；必要时用adb将App设为常驻；双进程守护作可选补充 |
| 低版本Android（4.4）兼容 | 中 | 按第3.3节决策表选内核；确认盒子实际版本后再定minSdk |
| 内存泄漏无法根除 | 中 | 每日定时重启兜底，这是工程上被广泛验证的实践 |
| 版权合规 | 低（自用）/高（商用） | 自用/内部展示风险低；对外商用必须使用有授权的源 |
